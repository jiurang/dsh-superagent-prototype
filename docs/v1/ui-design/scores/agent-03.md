## 具体优点与风险

### 03-linear-split
- **具体优点**：212px 项目轨道 + 40px 定高需求表 + 400px 常驻详情的分栏非常完整；选中 #124 后，确认（待确认时）/拆任务/关闭需求就地出现，拆分输入框直接位于「关联任务 3」下方，Attempt 只藏在任务详情的运行记录页签里；`↑/↓`、`S`、`D/R/A` 和 Ctrl+K 让高频操作几乎不用离开当前上下文。
- **具体风险**：任务页表格没有「所属需求」列，T-248 只有在详情里才看得到它属于 #121；1200px 下 400px 详情又把列表压到约 560px，中文标题截断后，用户很难从任务反推「需求是任务容器」，这是本方案最实质的层级缺口。

### 04-kanban-canvas
- **具体优点**：按 6 个任务状态分列，阻塞卡直接露出原因与已阻塞时长（如「等待运维开通跨域白名单 · 6 小时」），需求卡带任务完成进度；438px 右侧抽屉把执行/证据/评审分页，底部动作随状态变化；「系统」与「项目设置」用两套带「系统级/项目级」作用域标记的弹窗真正分开，是三者中设置分层最落地的。
- **具体风险**：6 列看板在 1200px 下放不下，1240px 截图里最右侧「阻塞」列已经要被横向滚动才能完整看到——最高优先级的状态反而被挤到屏幕外；列宽约 180px 时卡片标题两行截断、元信息只有 9–10px，日常扫读会明显吃力。

### 05-timeline-flow
- **具体优点**：sticky 项目上下文条（DEMO、4 个未关闭需求、待你/进行中/阻塞）让「我在哪个项目」始终成立；右侧「此刻」把待确认、阻塞、评审、记忆复核收成可直接点「确认/处理/评审/复核」的清单；任务 sheet 把 attempt、report、证据、评审合并成一条按日分组的时间线，是三者中最好的任务叙事。
- **具体风险**：任务页每行直接展示「最新尝试」（如「已交付 结束 · a-t1」「评审 运行中 · a-7f3」），与页面自己写的「尝试只进入任务详情」以及任务书「Attempt 不进入任务列表」的约束直接冲突；另外「系统设置」只出现在项目页的一句说明里，没有可进入的独立设置面，系统/项目分层实际未落地。

## 评分依据

- **03-linear-split**：信息层级 8.5，任务效率 9.5，视觉品质 8.5，可扩展性 8.5，实现可行性 8.5。加权未舍入值 **8.75 → 8.8**。它把最高频的确认、拆分、派发、验收压在一条列表—详情轴上，键盘与命令面板进一步缩短路径；扣分集中在任务表脱离需求上下文、微字号和窄列表。需求「关闭/重新打开/删除」在 API 映射表中缺少明确端点，落地时需补契约。
- **04-kanban-canvas**：信息层级 8.5，任务效率 8.5，视觉品质 9.0，可扩展性 8.0，实现可行性 8.0。加权 **8.45 → 8.5**。项目/系统分层、阻塞卡和抽屉都很成熟，但需求/任务是两套画布，层级靠切换与回指维持；6 列溢出、完成列膨胀、把拖拽映射为合法的 dispatch/retry/review/accept 动作，是主要扩展与实现成本。
- **05-timeline-flow**：信息层级 7.5，任务效率 8.0，视觉品质 9.5，可扩展性 8.0，实现可行性 7.5。加权 **8.10**。版式、字体与时间线质感三者最佳，「此刻」也是很好的分诊器；但默认页是活动流而非需求容器，任务列表泄露 Attempt，系统设置缺位，且统一活动流需要新增 `/activity` 读模型或在服务端做事件合并，实现风险最高。

## 推荐

**03-linear-split** — 它是三者中唯一把「项目 → 需求 → 任务 → Attempt」完整压进一套可键盘操作的分栏工作流、同时动作始终贴着对象的方案；修掉任务行的需求回指和过窄列表后，最适合作为落地主案。
