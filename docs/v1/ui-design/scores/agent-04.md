## 具体优点与风险

### 01-command-center

- **具体优点**：248px 项目轨常驻 + 388px 需求母版 + 同屏详情，把「先项目、后需求」直接写进布局；选中需求时，状态分组、任务构成、确认/拆任务/追加任务都留在原地，`1–7`、`J/K`、`N`、`⌘K` 进一步缩短高频路径；系统块（Worker 并发、默认模型）与每张项目卡的「项目设置 · 只影响此项目」也在视觉上分层。
- **具体风险**：密度以可读性为代价——正文 10–11px、元信息 8–9px，248px 左轨加 388px 母版后详情只剩约 560px；1200×900 下任务详情的证据与排查步骤需要嵌套滚动，长标题或 125% 缩放时会明显拥挤，且原型未覆盖列表虚拟化和完整焦点陷阱。

### 04-kanban-canvas

- **具体优点**：6 个任务状态列 + 需求进度卡 + 438px 抽屉把状态、所属需求与阻塞原因放在同一张画布上，阻塞卡直接露出「等待运维开通跨域白名单 · 6 小时」；系统设置与项目设置用两套带「系统级 / 项目级」作用域徽标的弹窗真正分开，「全部项目」还会按 DEMO / NEW_CENTER_APP 分泳道，避免跨项目混排。
- **具体风险**：1200px 目标宽度下 6 列被压到约 180px，最右侧「阻塞」列贴边，阻塞卡标题换行、原因被截断；用户必须横向滚动或点箭头才能看全最紧急的状态，而「完成」列卡片堆积时还会继续拉长列高。

### 05-timeline-flow

- **具体优点**：sticky 项目上下文条（DEMO、4 个未关闭需求、待你/进行中/阻塞）与右侧「此刻」把「我在哪个项目」和「现在轮到谁」固定在同一阅读路径；「此刻」按阻塞 → P0 待确认 → 评审 → 记忆复核排序，每项直接给处理/确认/评审/复核动作，任务 sheet 又把 attempt、report、证据、评审合并成一条按日分组的时间线。
- **具体风险**：系统设置层没有落地——全站没有系统设置入口或系统级面板，项目页只有一句「项目设置与系统设置在视觉上保持分离」的说明；同时任务页每行直接显示「最新尝试 · a-7f3」，与「Attempt 只出现在任务详情」的硬约束冲突。

## 评分依据

- **01-command-center**：信息层级 9.0，任务效率 9.2，视觉品质 8.5，可扩展性 8.1，实现可行性 8.4。加权 **8.725 → 8.7**。项目轨、需求母版与详情同屏，动作贴着对象出现，是三者中日常路径最短、层级最稳定的方案；扣分集中在 8–11px 微字号、1200px 下详情宽度和列表虚拟化/焦点管理。
- **04-kanban-canvas**：信息层级 8.6，任务效率 8.4，视觉品质 9.1，可扩展性 8.2，实现可行性 7.7。加权 **8.455 → 8.5**。卡片、状态色、留白和泳道形成最完整的视觉体系，需求进度与阻塞原因也直接可读；但 6 列在 1200px 下需要横向滚动，拖拽到任意列必须逐条映射为 dispatch/retry/review/accept，且原型中的「关闭需求」没有对应 API，落地成本高于 01。
- **05-timeline-flow**：信息层级 7.4，任务效率 8.0，视觉品质 8.4，可扩展性 7.6，实现可行性 7.6。加权 **7.810 → 7.8**。时间线叙事与「此刻」分诊是三者中最好的，sticky 项目条也最稳；但系统层缺位、任务列表泄漏 Attempt，加上 9.5–10.5px 弱对比元信息和 `/activity` 读模型的额外后端成本，压低了综合分。

## 推荐

**01-command-center** — 它在 1200px 内同时保住项目上下文、需求扫描和就地操作，确认、拆任务、派发、验收、评审都不离开当前对象，且实现映射基本落在现有 API 上；相比 04 的视觉优势，它赢在更完整的层级与更短的日常路径。
