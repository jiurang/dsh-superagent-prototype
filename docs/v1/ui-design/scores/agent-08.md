## 逐项说明

### 03-linear-split

- **具体优点**：212px 项目导航 + 40px 需求表 + 400px 详情栏形成了真正的工作台骨架：选中需求后确认、拆任务、改状态、看关联任务都在右栏完成，任务页的 Attempt/证据/评审也只在 Tabs 里出现，概览页的「需要你处理」还提供确认/重试/验收的行内动作，项目上下文全程不丢失。
- **具体风险**：400px 详情栏在 1200px 下只给列表留下约 560px，中文需求标题被大量截断，元信息字号下探到 9–10.5px；当标题较长或用户使用 125% 缩放时，扫读与精确点选会明显变差，而 notes 中的虚拟化与焦点管理又会进一步抬高实现成本。

### 05-timeline-flow

- **具体优点**：sticky 项目上下文条 + 承诺条 + 中央时间线 + 右侧「此刻」把“我在哪个项目、最近发生了什么、现在轮到我做什么”做成一条连续阅读路径；需求展开体原位显示任务与最新尝试，任务 sheet 顶部直接给出「等你评审 / 重试派发 / 验收通过」状态动作，动作确实贴近状态。
- **具体风险**：系统设置与项目设置只在项目页副标题里“说明”了分离，没有实际界面分层；同时任务页是未按需求分组的平表且行内没有派发/验收动作，所有任务操作都必须先打开 760px sheet，任务量增大后定位与处理会比母版-详情式布局慢。

### 02-editorial-workspace

- **具体优点**：编辑排版体系最有辨识度：66px 页题、项目身份带、86px 编号导引和「原始来意 / 验收要点 / 最新动态」让需求像一份可读的简报，任务页按需求分组，任务抽屉再用编号章节组织验收、尝试、证据、评审与审计，项目/需求/任务/Attempt 的深度非常清楚。
- **具体风险**：版面密度过低，1200×900 首屏需求页只能完整看到约 1.5–2 条需求，且需求卡不展示具体任务行，日常在 6 条需求、10 个任务之间定位和操作需要持续滚动与开关抽屉；8.5–10.5px 的元信息与偏淡的辅助色进一步放大了可读性风险。

## 推荐

**03-linear-split**：它最接近“可持续值守的 issue workspace”——项目上下文常驻、需求与任务详情同屏、拆任务和状态动作都贴着对象，信息层级、任务效率与实现可行性最平衡。
