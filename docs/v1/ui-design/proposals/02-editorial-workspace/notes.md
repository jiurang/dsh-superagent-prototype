# 02 · Editorial Workspace / 杂志式工作台

> 把工作台当成一份每天更新的刊物：项目是封面，需求是简报，任务是按需求排版的篇目，右侧抽屉是展开的批注页。

## 一、概念

当前页面最根本的问题不是「不够好看」，而是所有信息都站在同一个平面上：章节标题、项目、需求、任务、尝试和表单共享相近的字号、相近的间距、相近的容器。用户必须先读完内容，才知道自己在哪一层。

这个提案用「编辑排版」而不是「后台面板」来组织工作台：

- **封面 / Cover**：每个项目有一个自己的身份带。大字号短代码、项目名、状态、敏感级、根路径和项目级数字，先行回答「我在哪个项目里」。
- **简报 / Brief**：一条需求不是一行数据库记录，而是一页短简报：编号、状态、优先级、来意原话、需求说明、验收要点、最新动态、可用动作。
- **目录 / Contents**：概览右侧的「本期要目」把七个区域当成刊物栏目，给出数量与入口。
- **批注页 / Dossier**：需求与任务详情不挤进列表，而是在右侧抽屉里展开。背景仍然保留当前页面，用户不会失去上下文。
- **刊物信息 / Colophon**：页码式编号、期号、日期、细分隔线，让界面有编辑感，但不装订成复古装饰。

整体保持浅色纸面与单一朱红强调色。项目之间的关系靠「切换上下文」而不是「混排后筛选」来表达。

## 二、信息层级

| 层级 | 界面位置 | 表达方式 |
|---|---|---|
| 系统 | 顶部报头、全站检索、项目页底部的「系统 / 项目」边界区 | 期号与日期是小字，检索是细线输入；系统设置与项目设置明确分成两栏说明，不混进业务列表 |
| 项目 | 导航右侧项目切换器、每页的项目身份带、项目页的双封面 | 大字短代码 + 项目名称是页面最强的第二视觉焦点；所有需求、任务、收件、记忆、评审都只显示当前项目 |
| 需求 | 需求页的简报卡、右侧需求抽屉 | 左侧编号导引栏放编号与状态；正文按「优先级 → 来源 → 标题 → 说明 → 原话 → 验收 → 最新 → 动作」阅读 |
| 任务 | 任务页按需求分组、任务行、任务抽屉 | 任务永远出现在所属需求之下；任务类型、优先级、当前尝试只做一行导语，不抢标题 |
| 执行尝试 / 证据 / 评审 | 仅任务抽屉内，带编号的章节 | Attempt 不进入任务列表；证据、评审和事件都在详情中按时间与层级展开 |

### 关键决策

1. **取消「全部项目」混合列表。** 现有需求页用项目下拉筛选，用户仍可能在全项目列表里猜上下文。原型把当前项目放进导航和身份带，切换项目是显式动作；项目页负责选择，业务页负责当前项目内的工作。
2. **需求是任务的容器。** 任务页按需求分组，组头是需求编号与标题，任务行属于组内。这样「这条任务为什么存在」不需要打开详情也能看到。
3. **所有重要动作就近出现。** 确认需求在需求卡与需求抽屉里；拆任务在需求卡内就地展开；验收、派发、评审与删除在任务抽屉底部；收件「转为需求」在每封信旁。
4. **尝试、证据、评审只在正确深度出现。** 任务列表保持可扫读；详情抽屉承担执行事实，避免列表退化成日志表。
5. **阻塞与失败不隐藏。** 阻塞任务在概览数字、需求卡的「最新动态」、任务列表和任务抽屉里都有各自的表达；失败尝试使用朱红色状态与「需要关注」提示块。

## 三、版式与字体决策

### 网格

- 桌面目标 1200px，外壳最大 1240px，左右留白 40px，内容宽约 1120px。
- 概览采用不对称双栏：主栏 `1fr`，右栏 `334px + 28px` 内边距；右栏放「本期要目」和「最近活动」，模拟杂志的边栏。
- 项目页为双封面 `1fr 1fr`，每张封面由「艺术字封面区 + 信息区」组成。
- 需求简报采用 `86px` 编号导引栏 + 正文；任务页为需求组头 + 行式任务表。
- 抽屉宽 540px，固定在右侧，遮罩只压暗背景，不替换页面。

### 字体

- 中文展示与阅读：`Songti SC / Noto Serif CJK SC / Source Han Serif SC / STSong / SimSun` 系统衬线栈。
- 界面与控件：`PingFang SC / Microsoft YaHei / Noto Sans CJK SC` 系统无衬线栈。
- 编号、路径、会话、时间：`SFMono-Regular / Consolas / Menlo` 等宽栈。
- 大数字与拉丁短代码优先 Georgia：DEMO、NEW CENTER APP、指标数字都使用衬线显示字体，强化编辑感。

字号大致层级：

| 用途 | 字号 / 行高 |
|---|---|
| 页面标题（需求、任务、项目） | 66 / 1.0，移动端 42 |
| 项目封面短代码 | 62 / 0.88；长代码 38 / 1.02，按 `_` 断行 |
| 项目身份带标题 | 39 / 1.22；紧凑带 26 |
| 区域标题 | 24–26 / 1.3 |
| 需求简报标题 | 24 / 1.4 |
| 抽屉标题 | 31 / 1.35 |
| 正文与说明 | 12.5–14 / 1.72–1.85 |
| 元信息 / 状态 / 编号 | 8.5–10.5，字距 0.04–0.16em |

### 色彩与形状

- 纸面 `#f5f2ea`，抬高纸面 `#fbf9f4`，浅纸 `#ece7da`，墨色 `#1e1c17`，辅助墨 `#706a5e`，细线 `#ddd6c8`。
- 唯一品牌强调色朱红 `#9c3327`，只用于当前标签下划线、主按钮、来源引线、当前项目标记和阻塞/退回重点。成功、警告、信息使用低饱和语义色，不引入第二种品牌色。
- 不用渐变，不用深色模式。阴影只用于抽屉、弹窗与 toast。
- 按钮圆角 2px，标签做成方形「印章」；需求卡和任务表用 1px 细边框，分隔优先用线而不是层层嵌套盒子。这样避免了当前界面里轻量胶囊与卡片混用的扁平感。

### 留白与节奏

- 页面头部下方到身份带约 30px，身份带到正文 34px，区域之间 34–52px，卡片内边距 20–30px。
- 通过大标题、细线、小号字距、数字衬线和大量呼吸空间形成节奏；信息密度高的部分（尝试、证据）放进抽屉，主页面保持可读。

## 四、交互说明

### 导航与项目上下文

- 七个可点击 tab：概览 / 项目 / 需求 / 任务 / 收件箱 / 记忆 / 评审。当前项使用朱红下划线与更深的字色。
- 右上角「当前项目」打开项目切换 popover，列出两个项目的短代码、名称、状态、需求/任务数量和当前标记；切换后所有页面、计数、收藏范围和空状态一起更新。
- 项目页的两张封面可以直接进入对应项目的工作台；「当前项目」有独立标记。
- 项目页底部用「项目设置 / 系统设置」两栏明确边界：项目设置只影响当前项目，系统设置由宿主面板管理。

### 需求

- 点击需求标题或「打开简报」：右侧抽屉展示来源原话、说明、验收口径、关联任务和最近活动。抽屉中的任务可以继续打开任务详情，任务详情里的所属需求也可以回到需求。
- 点击「确认」：需求变为「已确认」，简报、计数与抽屉同步更新。
- 点击「拆任务」：在该需求卡内部就地展开「拆稿」区域，而不是在列表底部追加长表单。拆稿包含：
  - 一行一个任务的草稿框；
  - 实时任务数量、逐条预览；
  - 类型、优先级、验收标准；
  - 对「像一段话被拆开」的提示；
  - 拆出任务默认进入「就绪」，需求变为「已拆分」，列表切回全部并提示。
- 点击「新建需求」：右侧抽屉先只展示项目、标题、优先级三项，来源、说明、验收折叠在「补充来源、说明与验收（可选）」中。保存后进入需求页，新简报滚动到视野并短暂高亮。

### 任务

- 任务页按需求分组，组头可再次打开需求简报。任务行展示类型、优先级、当前尝试和状态，不展示 Attempt 表。
- 点击任务行：右侧任务抽屉显示验收标准、执行尝试（最新在前）、证据与产物、评审记录、事件与审计。操作固定在底部：派发/重新派发、重试、验收通过、写评审、取消任务、删除。
- 评审在抽屉内展开表单；提交后通过进入「待验收」，退回回到「进行中」，评审记录与事件同时更新。
- 删除使用自定义确认弹窗，不是浏览器 `confirm`。文案明确：任务从列表和统计中消失，但运行记录、证据与审计保留。
- 运行记录与空状态都有说明；没有尝试的任务会提示派发后出现第一条记录。

### 收件箱、记忆、评审

- 收件箱以「来信」版式展示原话；「转为需求」打开预填标题、来源与上下文的创建抽屉，保存后该信标记为已建需求；「忽略」从当前列表移除。
- 记忆卡支持项目内即时搜索、确认、退回；新建记忆进入「草稿」并明确复核状态。索引引用检查在数据层保留，原型以搜索与状态动作演示。
- 评审页突出待评审队列，并列出通过/退回账本；「写评审」直接打开对应任务抽屉并滚到评审表单。

### 全局细节

- 全站检索按当前项目过滤需求与任务，支持标题、描述、来源原话；`/` 或 `⌘/Ctrl + K` 聚焦搜索，Enter 打开第一条。
- `Esc` 依次关闭弹窗、抽屉、项目 popover 或搜索；关闭抽屉后焦点回到触发元素；抽屉/弹窗打开时锁定页面滚动。
- Toast 固定在左下，避免遮挡右侧抽屉底部动作；打开新抽屉时清除上一条提示。
- 空状态覆盖筛选无结果、无任务、无关联任务、无尝试、无证据、无评审等情况，并给出下一步动作。

## 五、React 映射

### 路由与状态

保留现有 `App` / `PanelProvider` / `SegmentedTabs` 结构，在 XG 业务范围内加入 `activeProjectId`：

```ts
type XgView = 'overview' | 'projects' | 'requirements' | 'tasks' | 'inbox' | 'memory' | 'reviews'
type DrawerState =
  | { type: 'requirement'; id: string }
  | { type: 'task'; id: string; review?: boolean }
  | { type: 'createRequirement'; prefill?: RequirementPrefill }
  | { type: 'createProject' }
  | { type: 'createMemory' }
  | { type: 'createInbox' }
  | null
```

- `activeProjectId` 放在 `PanelProvider` 或新的 `XgProvider`，由项目切换器写入；路由里只需保存页面和当前项目 id，刷新后仍能回到同一上下文。
- `drawer`、`splitId`、筛选状态放页面级 state；如果需要分享链接，可把 `req` / `task` 写进 route query，抽屉内容仍是同一套组件。
- 现有 `useXg` 继续负责 `/projects`、`/requirements`、`/tasks` 等读取；`useMutation` 继续负责确认、拆分、派发、验收、取消、删除。`useTaskDetail` 保持「打开详情才请求」的行为，避免任务列表把 Attempt 拉进来。

### 组件拆分

| 原型区域 | React 组件建议 | 复用 / 端点 |
|---|---|---|
| 报头、tab、搜索 | `EditorialHeader`、`ProjectSwitcher` | 复用 `Input`、`Button`、现有 tabs；搜索可先用本地过滤 |
| 项目封面与身份带 | `ProjectCover`、`ProjectBand` | `/projects`；数字由需求与任务列表聚合 |
| 概览 | `XgOverviewPage`、`MetricStrip`、`DecisionQueue`、`ContentsRail` | 由当前项目数据计算待确认/进行中/待验收/阻塞 |
| 需求列表 | `RequirementBrief`、`RequirementRail` | `/requirements`；筛选可在客户端或继续使用 query |
| 拆稿 | `SplitEditor` | 保留现有 `taskTitlesFromInput` 与 `POST /requirements/:id/split` |
| 新建需求 | `CreateRequirementDrawer` | `POST /requirements`；收件转需求走 `/inbox/:id/triage` 或同一表单 + 状态更新 |
| 任务列表 | `TaskGroup`、`TaskRow` | `/tasks` 按 `requirementId` 分组；不渲染 Attempt 列 |
| 任务详情 | `TaskDetailDrawer`、`AttemptList`、`EvidenceList`、`ReviewSection` | `useTaskDetail`；派发/重试/验收/取消/评审/删除继续走现有 mutation |
| 删除确认 | `DeleteTaskDialog` | 复用 `Modal`，语义保持 soft delete |
| 收件箱 | `InboxLetter`、`CaptureInboxDrawer` | `/inbox`、`/inbox/:id/ignore` |
| 记忆 | `MemoryNote`、`MemoryDrawer` | `/memory`、confirm/reject |
| 评审 | `PendingReviewCard`、`ReviewLedger` | `/reviews` + 任务的评审记录 |

### 数据映射与两处需要补的字段

现有 domain 已覆盖绝大多数展示：

- 项目：`shortCode`、`name`、`status`、`sensitivity`、`rootPath`、`updatedAt`，计数由需求与任务列表计算。
- 需求：`seqNo`、`title`、`status`、`priority`、`sourceNote`、`description`、`updatedAt`；原型的「原始来意」直接使用 `sourceNote`，「需求说明」使用 `description`（当前列表未展示，但字段存在）。
- 任务：`type`、`status`、`priority`、`acceptance`、`currentAttemptId`、`autoDispatch`、`acceptedBy/At`；Attempt 的 `stage` / `status` / `workerSessionId` / `lastReportAt` 全部来自详情；证据来自 `artifacts`，评审来自 `reviews`，事件来自 `events`。
- 收件箱：`channel`、`contact`、`rawContext`、`receivedAt`、`status`；项目内过滤。
- 记忆：类型、标题、内容、状态、来源、标签；确认/退回是现有端点。
- 评审：`decision`、`reviewer`、`comments`、`createdAt`。

**需求级验收要点**：现有 domain 的验收标准在 `Task.acceptance` 上，需求本身没有同名字段。原型为了让简报成立，在 mock 中给需求增加了 `acceptance`。实现时有两个选择：

1. 推荐：给需求增加可选 `acceptance`（或归入 description 的结构化字段），拆任务时作为默认值带入。需要一次后端小迁移。
2. 不改 schema：需求卡显示「首个任务的验收标准」或任务的验收摘要；未拆任务时显示「拆任务时补充验收口径」。本原型采用了方案 1 的视觉结果，但方案 2 也能保持阅读顺序。

**最新动态**：原型 mock 了 `activity`。React 落地时可由 `task.events` / `audit` 推导，或增加轻量的需求活动查询；在数据未就绪时至少显示「更新 {timeText(updatedAt)}」，不要留空。

### 样式实现

- 新样式建议包在 `.xg-editorial` 下，避免影响宿主其他面板；变量可从 `--dsw-alias-*` 映射出本地的 `--ed-paper`、`--ed-ink`、`--ed-rule`、`--ed-accent`，使深色宿主里仍能局部保持浅色纸面（本提案按需求只做浅色）。
- 现有 `dt-*` 控件可以继续用于表单与按钮，但页面级排版需要独立的 editorial 布局类，不建议在 `.dt-section` 上叠加过多覆盖。
- 抽屉必须渲染到 `body` 的 portal，避免被面板的 `overflow: auto` 裁掉；同时锁定 body 滚动、处理焦点回到触发元素。
- 字体全部使用系统栈，不加载外部字体；select 箭头用内联 data URI SVG，保持自包含。
- XG 页面可以把现有 960px 的 `.dt-column` 放宽到 1120px，或单独使用 1240px 外壳；1200px 桌面下内容仍留有 40px 安全边距。

### 落地顺序建议

1. 先抽出 `ProjectBand` 与 `RequirementBrief`，把需求页信息层级落地；
2. 接 `SplitEditor`（复用 `taskTitlesFromInput` 与现有拆分 mutation）；
3. 接 `TaskGroup` / `TaskDetailDrawer`，把 Attempt 移出列表；
4. 再接创建需求抽屉与项目切换器；
5. 最后做概览的编辑排版和收件/记忆/评审的版式化。这样每一步都能独立回归现有 API 语义。

## 六、为什么它比当前页面「不扁」

当前页面的层级主要依赖标签和筛选器：

- 区域标题只有 13px，和需求标题、任务标题的字号差距很小；
- 需求是一行标题 + 标签 + 元信息，来源与验收在列表里不成立；
- 创建需求与新建项目是列表底部的长表单；
- 任务详情在任务行下直接展开，Attempt 表、产物、评审与操作全部堆在同一深度；
- 项目上下文是一个筛选下拉，用户可以在混合列表中迷路。

本提案把这些关系变成可见的版面：

- **项目成为空间**：身份带、封面、项目切换器与项目级数字让上下文先于内容出现。
- **需求成为简报**：编号导引 + 大标题 + 原话引用 + 验收 / 最新动态，让一条需求可以被人「读」，而不是被「扫」。
- **任务成为归属物**：任务在需求组内，Attempt 只在抽屉里，列表和详情分工明确。
- **动作用位置表达重要性**：确认贴在需求项，拆稿在需求内展开，验收和删除在任务抽屉底部；表单从「列表下方」变成「上下文中的抽屉」。
- **层级由字体、线、留白和深度共同承担**：66px 的页标题、39px 的项目标题、24px 的简报标题、10px 的元信息；纸面、细线、编号和右侧抽屉形成连续的阅读深度，而不是所有信息压在同一层。

## 七、取舍与风险

- **衬线字体回退**：中文衬线依赖系统字体，Windows 下可能落到 SimSun；已在 1200px 下检查大字号不糊、不裁切。正式实现可继续使用系统栈，避免外部字体依赖。
- **微型字号**：元信息使用 8.5–10.5px 以保持编辑密度；生产环境建议将正文元信息下限提到 11px，并检查 125% / 150% 缩放。
- **需求验收字段**：这是本提案唯一需要产品/后端确认的 schema 变化；已给出不改表的降级方案。
- **活动数据**：最新动态需要有来源；没有活动查询时用 `updatedAt` 与审计事件兜底，避免伪造内容。
- **抽屉内跳转**：需求 → 任务会替换抽屉内容，当前没有面包屑历史。正式实现可加返回栈；原型保留两端的双向链接。
- **跨项目视图**：按设计去掉了混合需求/任务列表。若业务确实需要跨项目，应单独做「总览」，而不是恢复一个可以混排业务行的筛选器。
- **数据规模**：原型在客户端过滤与搜索；数据量上来后，需求/任务筛选应交给服务端，抽屉详情继续按需加载。
- **无外部资源**：原型没有字体、图片或 UI 库依赖，只有内联 data URI 的 select 箭头；React 版保持同样约束即可。
