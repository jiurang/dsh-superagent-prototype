# 04 · 看板 / 画布工作台

> 原型：`docs/v1/ui-design/proposals/04-kanban-canvas/index.html`
> 目标宽度：1200px 桌面视口；自包含 HTML / CSS / 原生 JS，无外部依赖。
> 模拟数据：`DEMO`（账单系统）、`NEW_CENTER_APP`（中心应用）。

## 1. 概念

这个方案把工作台理解为一张**摊开的工作画布**，而不是一列纵向堆叠的表单。

传统页面的顺序是「列表 → 点开详情 → 再返回列表」，项目、需求和任务的关系只能靠文字标签提示。看板方案把它们变成空间关系：

- 项目是画布上下文（顶部项目切换器）；
- 需求是一张有边界的卡片，拆出的任务会直接落到任务画布的「就绪」列；
- 任务卡用 `#124`、`#121` 这样的需求引用把上下文带回卡片；
- 执行尝试、产物/证据和评审不进入卡片，只在任务侧栏中出现，避免把执行细节撒到画布上。

视觉上使用**暖中性纸面**：米白画布、象牙白卡片、细线分隔、浅阴影。状态用低饱和的赭石、灰蓝、苔绿、灰紫、砖红表示，不使用大面积高饱和色。各列有独立的顶部状态色和列内背景，卡片是本方案中唯一的「硬边框 + 投影」层级，因此视觉分组很强。

## 2. 画布 / 列模型

### 2.1 外壳：系统与项目分开

- 顶部横条：品牌 + 7 个页面 tab（概览 / 项目 / 需求 / 任务 / 收件箱 / 记忆 / 评审）+ 全局搜索 + **系统**入口。
- 第二行项目条：`全部项目`、`DEMO`、`NEW_CENTER_APP`，右侧是执行器状态和**项目设置**。
- `系统` 与 `项目设置` 位于两个不同的区域，使用两种 modal：系统设置带「系统级 · 影响所有项目」标记，项目设置带「项目级 · 仅作用于当前项目」标记。连接、密钥、执行器属于系统；根路径、默认优先级、自动派发属于项目。

### 2.2 两种列

画布有两种模式，共用同一套卡片语言、列背景和侧栏：

| 模式 | 列 | 卡片必须显示 | 列内动作 |
|---|---|---|---|
| 需求流 | 待确认 / 已确认 / 已拆分 / 已关闭 | `#seq`、优先级、标题、来源、负责人、更新、任务完成度 | 确认、拆任务、关闭需求 |
| 任务流 | 就绪 / 进行中 / 评审 / 待验收 / 完成 / 阻塞 | 优先级、类型、标题、所属需求 `#seq`、负责人、更新；阻塞卡显示原因与时长 | 派发、重试、评审、验收、删除 |

需求状态符合 `REQUIREMENT_STATUSES`，任务状态符合 `TASK_STATUSES`（原型不展示「取消」列，取消后任务离开看板）。

### 2.3 项目泳道

- 选择单个项目时，看板是扁平列。
- 选择「全部项目」时默认打开**按项目分泳道**：每列内部再分 `DEMO` / `NEW_CENTER_APP` 两条 lane，lane 头显示项目色和数量；另一条 lane 无卡片时显示「此列暂无任务」。
- 也可以关闭泳道，变成跨项目的扁平列；这时每张卡片显示项目短代码。筛选与泳道可叠加。
- 泳道让「全部项目」不再是一锅混合列表，同时保留跨项目总览。

### 2.4 卡片结构

**任务卡**

```text
[P0] [开发]                    ⠿
历史账单导出 OSS 签名错误
#121 历史账单归档检索
⚠ 等待运维开通跨域白名单   6 小时
陈屿                          6 小时前
```

- 左上：优先级（P0–P3）与类型（设计 / 开发 / 排障 / 评审）。
- 标题最多两行；需求引用一行截断，避免窄列撑破。
- 阻塞卡显示砖红色原因条，不隐藏阻塞信息。
- 负责人、更新时间始终在卡片底部；自动派发用一个小的闪电标记表示。
- 卡片**不显示** attempt 计数、运行阶段或产物数量。这些属于详情，不进入任务列表。

**需求卡**

```text
#124 [P0]                     ⠿
月度账单自动重算失败重试
来源 · 运营反馈 · 企微群
━━━━━━ 1 / 7 任务完成   14%
林墨                          今天 09:42
```

- 未拆分时显示「尚未拆分」的虚线块，而不是假装有进度。
- 已拆分时用一条按任务状态着色的细进度条，直接显示需求的执行覆盖情况。
- 已关闭需求降低对比度，但仍留在列里，保留上下文。
- 需求卡不展示 attempt、证据和评审；这些只属于任务。

### 2.5 概览条与空状态

- 看板顶部有一条 58px 的紧凑概览：本轮视图（需求流 / 任务流）、当前项目、各列关键计数、本周完成进度、完整概览入口。
- 计数随项目切换和页面数据实时重算；不是静态插图。
- 空状态分三层：
  1. **页级 / 筛选级**：当筛选结果为 0 时，不渲染 6 个重复空列，而是一整块画布空状态，提供「清除筛选」和「新建任务/需求」。
  2. **列级**：单列为空时，显示虚线放置区与说明（如「暂无阻塞任务」）。
  3. **侧栏级**：任务没有运行记录、证据或评审时，各有独立的空状态和下一步提示。
- 收件箱、记忆、评审页面在筛选为空时也有明确的空状态。

## 3. 交互模型

### 3.1 导航与切换

- 7 个 tab 都是可点击的页面切换，当前 tab 用细的下划线标记。
- 项目 pill 立即切换上下文；需求/任务页会相应更新。切换项目时清空临时筛选，避免把 DEMO 的筛选条件误带到 NEW_CENTER_APP。
- 需求流 / 任务流可在画布右上角快速切换，等同于点击顶部的「需求 / 任务」tab。
- 筛选 chip：全部 / 我的 / P0–P1 /（任务）阻塞 或（需求）待拆分。
- 画布可横向滚动；工具栏左侧有左右滚动按钮，适合 6 列在 1200px 下略微超出时使用。

### 3.2 拖动推进状态

- 卡片可拖动，hover 时右上角出现抓手；拖动时卡片降低不透明度并轻微旋转。
- 列作为投放目标会高亮（虚线 + 状态色）。
- 放下后状态更新、卡片移动到目标列、出现可撤销 toast。
- **原型允许任意列之间的拖动**，用于演示空间交互；真实实现必须把它映射为后端允许的状态迁移（如「待验收 → 完成」只能走验收动作，「就绪 → 进行中」只能走派发），或者只对合法方向显示投放高亮。详见第 4 节。
- 需求卡同样可拖动，但从待确认直接拖到已拆分之类的操作在真实后端也应受状态机约束。

### 3.3 需求详情侧栏

点击需求卡打开右侧 inspector：

- 面包屑：项目 / 需求 `#seq` / 当前对象；
- 标题、状态、优先级、负责人、来源、更新时间；
- tabs：**详情 / 关联任务 / 动态**；
- 详情：需求描述、来源引用、任务覆盖进度、上下文元信息；
- 关联任务：按优先级排列的任务行，显示状态、类型、负责人；点击任务切换到任务详情；
- 动态：创建、确认、拆分与任务更新组成的时间线；
- 底部动作随状态变化：
  - 待确认：`关闭需求` / `拆任务` / `确认需求`；
  - 已确认：`关闭需求` / `拆任务`；
  - 已拆分：`关闭需求` / `继续拆分`；
  - 已关闭：`查看关联任务`，不再接受拆分。
- 待确认的「拆任务」与「确认」并排出现：允许先拆、后确认，但需求状态会在拆分后直接变成已拆分，保持与现有接口一致。

「关闭需求」会打开二次确认：说明已拆出的任务继续执行、运行记录和证据保留。需求不提供硬删除，避免错误地丢失任务容器。

### 3.4 拆分交互

拆分发生在需求侧栏内部，不跳页：

1. 点「拆任务」后，侧栏切换为拆分视图，顶部保留需求上下文。
2. 任务标题预填 3 条建议（来自当前需求的拆分提示），每行一个任务；行内逗号、分号不会被拆开，与 `taskTitlesFromInput` 语义一致。
3. 默认类型、默认优先级、验收标准可统一设置。
4. 输入时实时显示「将拆出 N 个任务」与标题 chip 预览；如果多行看起来像一段话被误拆，会出现提示（与现有 `splitLooksLikeProse` 逻辑一致）。
5. 提交按钮固定在侧栏底部（`form="split-form"`），始终可见。
6. 成功后：需求变为「已拆分」，任务进入任务画布的「就绪」列，侧栏切到「关联任务」，toast 报告数量；新任务有短暂的入场高亮。

### 3.5 浮动新建器

右下角固定的浮动新建器不是普通按钮，而是一个**不离开画布**的 composer：

- 点击展开；`新建任务 / 新建需求` 两个 mode。
- 任务：必须选择所属需求；项目、需求、优先级、类型、验收标准都在一个面板里。
- 需求：项目、优先级、来源 / 背景；提交后落在「待确认」。
- 从收件箱点「转需求」时，同一个 composer 以需求模式打开，预先填好标题、上下文和项目，并显示「从收件箱 … 转入」提示；提交后收件项从收件箱移除。
- 支持点击画布外部收起、`Esc` 收起、`C` 打开。
- 新建成功后自动切到目标画布、选中对应项目，并高亮新卡片；toast 说明落入了哪一列。

### 3.6 任务详情侧栏

点击任务卡打开：

- 标题、状态、优先级、类型、负责人、更新时间和 `T-xxx` 编号；
- 阻塞任务顶部显示阻塞 banner（原因 + 已阻塞时长）；
- 验收标准单独成块；
- tabs：**执行 / 证据 / 评审**，括号里是数量；
- 执行：当前尝试、执行器 Session、阶段、最近报告；运行记录按尝试展开（开始时间、Session、模型、报告/失败原因）；
- 证据：产物与证据列表，按类型（代码 / 文档 / 证据 / 复盘）显示，点击行展开预览；
- 评审：历史评审记录（通过 / 退回、评审人、意见、时间），任务在评审状态时提供内联评审表单；
- 底部根据状态提供动作：派发 / 重试 / 查看证据 / 去评审 / 验收通过 / 查看产物；始终可以删除。
- 任务详情内可以点 `所属需求` 回到需求侧栏，形成双向路径。

### 3.7 删除确认

删除任务会打开真正的确认对话框：

- 说明任务会从看板和统计中移除；
- 说明运行记录、证据和评审仍保留在审计中；
- 显示任务编号、项目、需求、负责人，避免删错；
- 确认后关闭侧栏，toast 提供**撤销**；撤销恢复卡片和统计。
- 需求只提供「关闭需求」确认，不做硬删除。

### 3.8 其他页面与键盘

- 概览：需要你处理的 3 件事、执行器状态、项目入口、本周节奏、分两列的最近活动。
- 项目：项目卡包含统计、进度、路径、成员、项目设置和打开画布；系统级配置独立成一条说明带。
- 收件箱：未处理消息、转需求、忽略、手动记录。
- 记忆：按项目和状态筛选，确认 / 退回待复核记忆，展示引用健康。
- 评审：按决策筛选，点任务标题回到任务详情。
- 键盘：`Esc` 关闭最上层浮层（搜索 → modal → 侧栏 → composer），`Ctrl/Cmd + K` 搜索，`C` 新建；卡片支持 Enter / Space 打开。

## 4. React 映射

### 4.1 路由和状态

现有 `src/client/app.tsx` 已经有 7 个 tab 的 `Route` / `TABS`，无需改变一级信息架构：

```text
overview      -> <OverviewPage />
projects      -> <XgProjectsPage />
requirements  -> <XgBoardPage mode="requirements" />
tasks         -> <XgBoardPage mode="tasks" />
inbox         -> <XgInboxPage />
memory        -> <XgMemoryPage />
reviews       -> <XgReviewsPage />
```

建议把 `projectId`、`view`、`filter` 放进 URL query（与现有 settings 的 `query` 类似），侧栏、composer、modal 保留在组件本地 state：

```text
?project=demo&view=tasks&filter=mine
```

这样刷新、分享和后退都能回到同一个画布位置。当前 `App` 的 back stack 可直接沿用。

### 4.2 组件拆分

```text
<XgBoardPage>
  <ProjectScopeBar />           // /projects + 执行器状态 + 项目设置
  <BoardHeader />               // 面包屑、标题、视图切换、新建
  <BoardOverviewStrip />        // 各状态计数 + 本周完成
  <BoardToolbar />              // 筛选 + 横向滚动
  <Board>
    <BoardColumn status="就绪">
      <BoardLane project="demo" />   // 仅全部项目模式
      <TaskCard /> / <RequirementCard />
      <ColumnEmptyState />
    </BoardColumn>
  </Board>
  <RequirementDrawer> ... </RequirementDrawer>
  <TaskDrawer> ... </TaskDrawer>
  <FloatingComposer> ... </FloatingComposer>
  <ConfirmDialog> ... </ConfirmDialog>
</XgBoardPage>
```

侧栏内容建议直接复用 `panel.tsx` 中已经成型的 `TaskDetailView` 子块（运行记录、产物、评审、事件），但将它们改成 tab 分组，并把 `TaskDetailView` 从列表展开区域移动到右侧抽屉。拆分表单沿用现有 `taskTitlesFromInput` 与 `splitLooksLikeProse`。

### 4.3 数据与 API 映射

| 原型动作 | 现有接口 / 组件 | 说明 |
|---|---|---|
| 读取项目 | `GET /projects` + `XgProjectsPage` | 项目 pill 只切换作用域，不重新发明项目对象 |
| 需求列 | `GET /requirements?projectId` | 一次取全量并按 `status` 分组，避免 6 个状态各发一次请求 |
| 任务列 | `GET /tasks?projectId` | 一次取全量并按 `status` 分组；过滤在客户端完成 |
| 确认需求 | `POST /requirements/:id/confirm` | 成功后 reload 需求 |
| 拆分任务 | `POST /requirements/:id/split` | `tasks[]` 包含 title/type/priority/acceptance |
| 任务详情 | `GET /tasks/:id` | 只在侧栏打开时请求；Attempt 只在详情展示 |
| 派发 / 重试 / 取消 | `POST /tasks/:id/dispatch` / `retry` / `cancel` | 与现有 `panel.tsx` 的动作语义一致 |
| 验收 | `POST /tasks/:id/accept` | 完成后进入「完成」列 |
| 评审 | `POST /tasks/:id/review` | 通过 → 待验收；退回 → 进行中 |
| 删除任务 | `POST /tasks/:id/delete` | 软删除；运行记录、证据和审计保留 |
| 记忆 | `GET /memory`、`confirm`、`reject` | 继续使用现有 `XgMemoryPage` 逻辑 |
| 评审列表 | `GET /reviews` | 任务标题 + 决策 + 评审人 + 意见 |
| 收件箱 | `GET /inbox`、`triage`、`ignore` | 转需求复用 composer 或现有 triage 表单 |

新建任务在当前 `panel.tsx` 中没有独立的「直接创建任务」入口。原型把它放在 composer 里，是产品层的建议；落地时有两种方式：

1. 仍走 `POST /requirements/:id/split`，提交一个任务的 `tasks` 数组；
2. 若 API 增加 `POST /tasks`，再改为独立端点。

**不要在 React 实现里伪造一个不存在的状态接口。**

### 4.4 拖动实现

- 原型使用原生 HTML5 drag / drop。React 中可以用同样的 API，或统一用 pointer events，不引入第三方库。
- **不要把「拖到任意列」直接翻译成「更新 status」**。当前后端提供的是派发、重试、评审、验收、取消这类动作端点。拖拽应映射为已允许的动作：
  - 就绪 → 进行中：dispatch；
  - 阻塞 → 进行中：retry；
  - 评审 → 待验收：review 通过；
  - 待验收 → 完成：accept。
- 对没有语义的投放（例如完成 → 就绪）不显示投放高亮，或打开任务详情让用户选择合法动作。
- 拖拽采用乐观更新 + 失败回滚，成功后刷新任务和需求统计；undo toast 是客户端层面的快捷撤销，最终仍以服务端状态为准。

### 4.5 样式映射

原型为了可独立打开，使用了一组局部变量（`--canvas`、`--paper`、`--line`、`--ink`、`--rust`...）。迁移到工作台时换成 DSH token：

| 原型变量 | 工作台 token |
|---|---|
| `--canvas` | `--dsw-alias-bg-base` / 页面底色 |
| `--paper` | `--dsw-alias-bg-layer-2` |
| `--paper-2` | `--dsw-alias-bg-module-platform` |
| `--line` / `--line-strong` | `--dsw-alias-border-l3` / `l4` |
| `--ink` / `--ink-2` / `--muted` | `--dsw-alias-label-primary` / `secondary` / `tertiary` |
| `--rust` | `--dsw-alias-button-primary-fill` |
| 阻塞 / 警告 / 完成 | `--dsw-alias-state-error-primary` / `warn-primary` / `success-primary` |
| 进行中 / 评审 | `--dsw-alias-state-business-primary` / `warn-primary` |
| 卡片阴影 | `--dsw-elevation-soft` + 一层细边框 |

暖色画布可以用 `color-mix` 或一层很淡的暖色叠加保留，不要依赖固定十六进制颜色，以免和现有浅色/深色主题冲突。

### 4.6 布局与可达性

- 1200px：6 列最小 180px，9px gap；4 列需求列会自动变宽。列高由内容撑开，使用 flex stretch 让同一屏的列底边对齐，但不强制固定高度。
- 侧栏宽度 438px，挂在视口右侧，不挤压画布；打开时页面滚动锁定，Escape 关闭。
- 焦点：打开侧栏后焦点进入 drawer，关闭后回到触发卡片（实现时记录 `document.activeElement`）。原型的确认弹窗和抽屉都支持 Escape。
- 拖拽有键盘替代：卡片支持 Enter 打开详情，操作按钮提供同样的状态迁移；不把拖拽作为唯一路径。
- 性能：已用 23 个任务的原型验证；真实项目可能出现数百张完成卡，建议「完成」列默认折叠到最近 N 张并提供“查看全部”，或使用窗口化渲染。每列独立渲染，避免整板无意义重排。

## 5. 层级如何变得可见

README 要求把系统 → 项目 → 需求 → 任务 → Attempt 的层级显性化，这个方案用四层视觉线索做到：

1. **系统 / 项目分开**：系统设置在顶部工具区，项目设置贴着项目条；文案分别标明「系统级 · 影响所有项目」和「项目级 · 仅作用于当前项目」。
2. **项目是第一层上下文**：顶部项目 pill 始终可见；选中「全部项目」时强制按项目分泳道，而不是在同一条列里猜每个任务属于谁。
3. **需求是任务容器**：需求卡显示「1 / 7 任务完成」与状态色进度；任务卡用 `#124` 回指需求；任务详情底部有「所属需求」，需求详情里有「关联任务」，双向可走。
4. **Attempt 只在任务的详情里**：卡片只显示状态、优先级、类型、负责人和更新时间，不显示 attempt 数/阶段；运行记录、证据和评审全部在任务侧栏的 tab 内。这样画布保持可扫读，执行细节在需要时展开。
5. **动作就近**：确认、拆分在需求侧栏；派发、重试、验收在任务侧栏；新建在右下角浮动 composer；删除在任务底部。没有把所有动作堆到页面底部的表单里。

## 6. 原型边界

- 所有数据在前端内存中；刷新页面回到初始 mock，删除、关闭、拆分、评审都不会持久化到后端。
- 需求「关闭」、任务「删除」、拖动状态迁移都实现了二次确认或可撤销的演示，但真实规则需要后端状态机与权限校验承接。
- 搜索与命令快捷键只覆盖 mock 需求、任务和项目；真实实现应调用现有 `GET search`。
- 侧栏的焦点陷阱、完整 ARIA 对话框管理、移动端覆盖布局是下一步实现项；本原型重点验证 1200px 桌面信息架构和关键交互。
- 没有引入图标库：所有图标是内联 SVG；没有外部字体与图片。
