# 01 · Command Center / 驾驶舱

> 一个人的项目驾驶舱：多项目在左，当前项目在上，需求与任务在右。
> 原型：`index.html`（自包含，无外部字体 / 图片 / 依赖）。

## 1. 概念

这个方案把工作台当成**单人值守的操作台**，而不是一组业务表单：

- **左侧是项目组合**：始终可见，切换项目不离开当前工作区；
- **顶部是当前项目的仪表**：运行、就绪、阻塞、记忆待复核四个信号；
- **中间是工作区**：需求与任务都采用「列表 + 详情」的母版/细节结构；
- **动作靠近对象**：确认需求在需求头上，拆任务在需求详情里，派发/验收/评审在任务详情里，删除有独立确认。

驾驶舱的隐喻只落在两处：项目卡上的 12 天节律 sparkline，以及概览里的执行脉搏卡。其余部分保持安静的纸张质感、细边框和低饱和状态色，避免「仪表盘贴纸」式的装饰。

三个项目刻意承担不同演示职责：

| 项目 | 初始数据 | 演示重点 |
|---|---|---|
| `DEMO` 账单系统 | 6 需求 / 6 任务 | 主流程：待确认、拆任务、阻塞、评审、验收 |
| `NCA`（`NEW_CENTER_APP`）中心应用 | 5 需求 / 4 任务 | 项目切换、跨项目上下文、待评审与阻塞 |
| `OPS` 运维脚本库 | 1 需求 / 0 任务（暂停） | 暂停/空状态，以及「任务由需求拆出」的完整空页 |

初始的 `DEMO` 顶部读数为：**运行中 1、就绪 1、阻塞 1、记忆待复核 2**。顶部只统计当前项目；左侧「全部项目 · 脉搏」才统计三个项目，两个范围都明确标注，避免数字打架。

## 2. 版式与尺寸

目标桌面宽度 1200px，最小约 1020px 仍可用。

```text
┌────────────────────── 1200 ───────────────────────┐
│ rail 248 │ status strip 54                          │
│          ├ header: eyebrow / 标题 / 摘要 / tabs      │
│          ├ master 388 │ detail（剩余宽度）           │
│          ├ keybar 27                                │
└─────────────────────────────────────────────────────┘
```

- **左轨 248px**：品牌、3 张项目卡（sparkline + 运行/阻塞）、全部项目脉搏、系统边界、操作者与 ⌘K。
- **状态条 54px**：`DEMO`、项目名、健康、当前项目四个指标、同步状态、搜索。
- **页头**：层级眉标（`DEMO · 账单系统 / 需求层`）、页面标题、计数摘要、右侧说明/动作、7 个 tab。
- **母版 388px**：项目上下文、标题、状态筛选、可滚动卡片列表、底部 J/K 提示。
- **详情**：独立滚动；头部固定，正文按「语境 → 任务构成 → 执行 → 证据 → 评审」渐进展开。
- **底部键条 27px**：数字切换、J/K、N、⌘K、Esc；右侧是同步与当前项目。

需求/任务/收件/记忆/评审使用相同的分栏语法，但**详情内容按对象不同**，不是同一个模板换字段。

## 3. 信息层级

### 3.1 系统 / 项目

- 左轨底部是独立的「系统 · 全部项目」块：Worker 并发、默认模型。
- 项目页每张卡底部写「项目设置 · 只影响此项目」。
- 项目页下方是虚线、斜纹的「系统设置 · 影响本实例所有项目」，与项目卡在视觉上分层，且不是同级卡片。
- 需求页/任务页的项目 mini 卡只承载根路径、敏感级、健康，不混入系统设置。

### 3.2 需求

需求是任务的容器，不只是一个列表项：

- 列表按 **待确认 → 已确认 → 已拆分 → 已关闭** 分组，组头带解释（等你拍板 / 可拆任务 / 任务在流转 / 已收口）。
- 卡片带来源、优先级、更新时间，以及由任务状态拼成的小进度轨。
- 详情头部有生命周期轨迹：`待确认 → 已确认 → 已拆分`。
- 详情正文才出现「任务构成」；任务行可跳到任务页。
- 拆任务在详情内部展开，不跳到别的页面，也不把表单堆到页面底部。

### 3.3 任务与 Attempt

- 任务列表按**操作优先级**分组：阻塞 → 评审 → 待验收 → 进行中 → 就绪 → 完成。
- 列表只显示状态、类型、优先级、来源需求、阻塞原因/更新时间；**不显示 Attempt 列表**。
- 点击任务后，右侧详情出现：
  - 验收标准与规格；
  - 执行尝试（阶段轨、Worker session、最近报告、tokens、attention）；
  - 证据/产物；
  - 评审与评审表单；
  - 折叠的排查步骤与事件。
- 阻塞任务有顶部红色状态轨、列表中红色提示条、详情中的阻塞横幅；不需要展开才知道风险。

### 3.4 状态与颜色

颜色只做辅助，每个状态都有文字：

| 语义 | 颜色 | 使用位置 |
|---|---|---|
| 进行中 / 完成 | 绿 `#2d7a58` | 任务、项目 sparkline、健康 |
| 就绪 / 未处理 | 灰绿 `#838b84` | 排队、未处理 |
| 阻塞 / 删除 | 红 `#a53c30` | 阻塞、危险动作 |
| 待确认 / 待验收 | 琥珀 `#a46b16` | 等人动作 |
| 评审 | 紫 `#62508c` | 人工评审关口 |
| 交互 / 当前 | 铁锈 `#bc5430` | 选中、焦点、当前阶段 |

底色使用暖纸色 `#f2efe7` / `#f8f6f0`，左轨使用近黑绿 `#151c19`。主要按钮用墨色，不把铁锈色当成大面积主按钮，保持「安静但有信号」。

## 4. 页面说明

### 概览 / 驾驶舱

- 顶部一句话叙事：`8 件待你处理，1 条执行线在跑。` 并解释当前最大风险。
- 「待你处理」按紧急度排列：阻塞 → 待确认 → 评审 → 验收 → 拆任务 → 记忆。每行直接给动作。
- 深色脉搏卡展示唯一在跑的任务、阶段轨、已运行时间、tokens、尝试次数、Worker。
- 最近活动按时间倒序，动作后立即插入「刚刚」。
- 收件箱作为单独的「转需求或忽略」入口，不混进 8 件人工动作里。

### 项目

- 每张项目卡：健康、12 天节律、需求/任务/运行/阻塞、根路径、默认优先级、自动派发、Worker 模型、当前项目标记。
- 「系统设置」独立虚线区，说明模型/来源/并发/部署影响全部项目。

### 需求（重点）

- 母版头：项目 mini、需求计数、新建入口、五个状态筛选。
- 需求卡：编号、优先级、标题、来源、拆解进度、阻塞数量、更新时间。
- 详情头：状态、优先级、项目/来源/任务数、生命周期、确认/拆任务/追加任务/查看任务。
- 详情体：需求描述、来源原话、任务构成、拆任务 composer。
- 新建需求使用右侧抽屉：项目锁定当前上下文、标题必填、来源/描述/优先级、最近需求避免重复、「填入示例」、⌘↵ 提交。创建后进入「待确认」并选中新需求。

### 任务

- 母版头：项目 mini、任务计数、七个状态筛选。
- 卡片：状态轨、类型、优先级、编号、标题、来源需求；阻塞卡显示 attention。
- 详情：状态轨、生命周期、阻塞横幅、验收标准/规格、尝试、证据、评审、排查、事件、软删除入口。
- 项目暂停时，任务仍可查看、评审或验收，但派发/重试被禁用，并出现「恢复项目后才能派发」的提示。
- 空项目（OPS）显示整页的场景化空状态：确认需求 → 拆成任务 → 派发 Worker，并保留新建需求入口。

### 收件箱 / 记忆 / 评审

- **收件箱**：左侧未处理渠道消息，右侧原文 + 转需求表单；转出后进入待确认，原消息移出队列。忽略不弹确认（非破坏性）。
- **记忆**：按待复核/已确认/已废弃分组；详情显示内容、来源、引用文件与校验状态；确认/退回就近出现；「检查引用」是页头动作。
- **评审**：左侧「待我评审」按任务聚合，下方历史结论；右侧先看验收标准、最近一次尝试和证据，再在同一区域提交通过/退回。退回必须写意见。

## 5. 交互与演示脚本

原型里所有关键动作都可点击：

1. **切换项目**：点左轨任一项。顶栏、页头、tab 计数、需求/任务/收件/记忆/评审全部切到该项目；保留当前 tab（例如从需求切到 NCA 需求）。
2. **打开需求**：点需求卡；母版选中态、右侧详情、任务构成同步。也可用 J/K 在列表中移动选中项。
3. **新建需求**：页头「新建需求」、`N` 或空状态入口 → 右侧抽屉；输入标题后可提交，`⌘/Ctrl+↵` 也可提交；「填入示例」填充当前项目的示例。提交后新需求进入待确认并被选中。
4. **确认需求**：待确认详情头「确认需求」→ 状态变已确认，组计数、tab 计数、概览待办更新。
5. **拆任务**：在 #124 或新需求详情点「拆任务」→ 内联 composer。任务标题一行一个，实时预览数量；类型/优先级为分段选择；验收标准应用于本次全部任务。提交后需求进入已拆分，任务出现在任务页，需求构成立即更新。
6. **任务详情**：任务列表点任一任务；阻塞任务展示 attention、triage、重试；就绪任务可派发；评审任务可打开评审表单；待验收任务可验收。每次动作都更新任务状态、tab 计数、左轨运行/阻塞数、需求进度。
7. **删除确认**：任务详情底部「删除任务」→ 自定义 modal，明确说明软删除与保留审计；取消 / 确认。确认后任务从列表、需求构成和统计中移除，运行记录保留（原型用 toast 说明）。不使用 `window.confirm`。
8. **收件分流**：收件详情表单「建立需求」→ 新需求进入待确认；「忽略此条」移出队列。
9. **记忆**：待复核项可确认/退回；`检查引用` 触发一次引用校验并写入活动。
10. **评审**：评审 tab 或任务详情提交通过/退回；通过 → 待验收，退回 → 进行中，并进入历史结论。退回空意见会提示并阻止提交。
11. **命令面板**：⌘K / Ctrl K / `/` 打开；↑↓ 选择、↵ 执行、Esc 关闭。包含新建需求、查看阻塞、处理收件、复核记忆、检查引用、当前项目需求和任务、其他项目切换。
12. **键盘**：`1–7` 切 tab、`J/K` 浏览列表、`N` 新建需求、`⌘/Ctrl+↵` 提交当前表单、`Esc` 关闭 drawer/modal/composer。抽屉打开时焦点进入标题，删除 modal 默认聚焦取消。

### 可直接打开的演示状态

## 6. 映射到 React / API

### 6.1 组件结构

建议把驾驶舱外壳放在所有 xg 页面之上，而不是每个页面各渲染一次 rail：

```tsx
<XgCommandCenter>                    // 项目上下文、tab、overview 数据
  <ProjectRail                       // 左轨 + 全部项目脉搏
    projects={projects}
    activeId={projectId}
    counts={railCounts}
    onSelect={selectProject}
    onOpenPalette={openPalette} />
  <StatusStrip                       // 当前项目四指标
    project={project}
    counts={projectCounts}
    onMetric={...} />
  <WorkspaceHeader
    tab={tab}
    counts={projectCounts}
    onTab={...}
    onNewRequirement={openDrawer} />
  <main>{tab === 'requirements'
    ? <RequirementWorkspace ... />
    : tab === 'tasks'
      ? <TaskWorkspace ... />
      : ...}</main>
  <CommandKeyBar />
</XgCommandCenter>
```

拆成这些可复用组件：

| 组件 | 职责 | 数据 |
|---|---|---|
| `ProjectRail` / `ProjectCard` | 项目切换、sparkline、运行/阻塞 | `GET /projects` + 项目计数 |
| `StatusStrip` | 当前项目四指标与跳转 | 由需求/任务/记忆计数派生，或专用汇总 |
| `RequirementMaster` / `RequirementCard` | 状态分组、筛选、选择 | `GET /requirements?projectId` |
| `RequirementDetail` | 语境、生命周期、任务构成、动作 | 选中需求 + `GET /tasks?projectId`（或按需求缓存） |
| `NewRequirementDrawer` | 创建表单、示例、最近需求 | `POST /requirements` |
| `SplitTaskComposer` | 多行标题、预览、类型/优先级/验收标准 | `POST /requirements/:id/split` |
| `TaskMaster` / `TaskCard` | 操作分组、状态筛选、选择 | `GET /tasks?projectId&status` |
| `TaskDetail` | 验收/规格、阻塞横幅、动作 | `GET /tasks/:id` |
| `AttemptTimeline` | 每次尝试、阶段、Worker、tokens | `detail.attempts` |
| `EvidenceGrid` | 产物卡片，只读 | `detail.artifacts` |
| `ReviewPanel` / `ReviewForm` | 评审记录与通过/退回 | `POST /tasks/:id/review` |
| `DeleteTaskDialog` | 软删除二次确认 | `POST /tasks/:id/delete` |
| `InboxWorkspace` | 原文、转需求、忽略 | `GET /inbox?status=未处理`、`POST /inbox/:id/triage|ignore` |
| `MemoryWorkspace` | 分组、来源、引用、确认/退回 | `GET /memory`、`POST /memory/:id/confirm|reject` |
| `ReviewWorkspace` | 评审队列 + 历史 | `GET /reviews` + `GET /tasks/:id` |
| `CommandPalette` | 快速跳转/动作 | 已加载列表 + 客户端过滤 |
| `Sparkline` / `StatusPill` / `Kbd` / `Drawer` | 视觉原语 | 无 |

现有 `controls.tsx` 的 `Button/Input/Tag/Pill/Modal` 可以复用；需要新增的是 Drawer（或扩展 Modal 的侧滑形态）、状态 pill、sparkline、Kbd、命令面板。不建议引第三方 UI 库。

### 6.2 状态与路由

- 项目是 URL/路由上下文：`project=DEMO`。否则刷新后无法保持「先项目、后对象」。
- 选中对象也应是路由参数（`reqId` / `taskId` / `inboxId` / `memoryId`），这样链接、返回栈和通知跳转都成立。
- 局部状态：`statusFilter`、`drawerOpen`、`splitOpen`、`reviewComposerOpen`、`paletteOpen`、`deleteTaskId`。
- 列表与详情共享一个选中 id；不要复制一份详情对象，避免 mutation 后双源。
- 计数从**同一个数据源**派生；若使用 `/overview`，明确它是否是全局的，不能与「本项目」混用。

原型里的 `?tab=&project=&req=&task=&split=&review=&drawer=&palette=&delete=` 只是评审便利，不作为后端契约。

### 6.3 API 对应

| 交互 | 端点 |
|---|---|
| 项目列表 / 当前项目设置 | `GET /projects`、`GET /projects/:id/settings` |
| 项目切换后的计数 | 来自已加载列表，或扩展 `GET /overview` 为按项目返回 |
| 需求列表 / 状态筛选 | `GET /requirements?projectId&status` |
| 新建需求 | `POST /requirements` |
| 确认需求 | `POST /requirements/:id/confirm` |
| 拆任务 | `POST /requirements/:id/split`，body `{ tasks: XgTaskSplitInput[] }` |
| 任务列表 | `GET /tasks?projectId&status` |
| 任务详情 | `GET /tasks/:id`（点击时懒加载，Attempt 不进入列表） |
| 派发 / 重试 / 验收 | `POST /tasks/:id/dispatch`、`/retry`、`/accept` |
| 提交评审 | `POST /tasks/:id/review` |
| 删除任务 | `POST /tasks/:id/delete`（软删除） |
| 规格 | `POST /tasks/:id/spec`（原型只读展示，编辑可后续补） |
| 收件转需求 / 忽略 | `POST /inbox/:id/triage`、`POST /inbox/:id/ignore` |
| 记忆确认 / 退回 / 校验 | `POST /memory/:id/confirm`、`/reject`、`POST /memory/verify` |
| 评审历史 | `GET /reviews?projectId` |

实现时沿用现有 `useXg`、`useTaskDetail`、`useMutation` 的加载/错误/忙状态模式；派发、评审、删除等 mutation 用按钮 busy 态防重复，成功后刷新列表或做单条乐观更新。

**评审状态**在原型里做了本地推进（通过→待验收、退回→进行中）。真实实现应以接口返回的 `task` 为准，不要硬编码；如果服务端过渡不同，以服务端为准。

**没有伪造的动作**：现有契约没有需求关闭/删除接口，所以原型不展示对应按钮；任务删除是契约中已有的软删除。系统设置页超出本次 tab 范围，只在视觉上表达其与项目设置的分层。

### 6.4 样式落点

- 建议新增 `src/client/xg/command/command.css` 或扩展 `xg.css`；使用现有 `--dsw-alias-*` token，映射成驾驶舱别名（rail/paper/status 色）。
- 断点：≤1180 缩窄左轨与母版；≤1020 隐藏页头说明、收窄母版、项目页变单列。
- 列表超过约 100 条时加虚拟滚动；当前 6 条的动效和分组实现不需要。
- 复用现有 `.dt-*` 的 focus-visible、禁用态、错误文案；新增抽屉/弹窗时补焦点陷阱与关闭后焦点返回。

## 7. 它替代了什么平铺模式

现有实现（`src/client/xg/panel.tsx`）的主要问题：

- **`XgRequirementsPage`**：项目筛选只是 section 头的一个 select；需求是一个全项目混合的扁平列表；拆任务表单嵌在对应行内；新建需求表单固定堆在页面最底部。用户需要先读完整个列表，再滚到底部新建，再回到列表找回来。
- **`XgTasksPage`**：一个扁平任务列表，点击行后在行内展开完整详情，Attempt 表格、产物、排查、评审、事件全部堆在展开体里；没有项目上下文栏，左侧列表仍然混着所有项目；执行尝试出现在列表区域。
- **`XgProjectsPage`**：卡片 + 底部表单，项目设置与系统设置没有在视觉上分成两层。
- **`app.tsx`**：只有全局 tab，项目不是一等上下文；所有 xg 页面各自渲染 section。

驾驶舱用四件事替换它：

1. **持久项目 rail**：项目是第一层上下文，先选项目，再看需求/任务；
2. **母版 + 详情**：对象在左侧被浏览，完整语境在右侧展开，动作不再滚到页面底部；
3. **状态分组 + 状态轨**：阻塞、待确认、评审等直接成为版式结构，而不是藏在 tag 里；
4. **就近动作**：确认在需求头，拆分在需求详情，派发/验收/评审在任务详情，删除有独立确认。

## 8. 取舍与风险

- **密度 vs 字号**：为了在 1200px 容纳母版 + 详情，正文下探到 10–11px、元信息 8–9px。浏览器 100% 下仍可读，但若宿主经常缩放到 80% 或用户视力受限，应整体放大 1–2px 并接受更多滚动。原型没有做字号切换。
- **母版宽度**：388px 能容纳状态、来源和三行卡片信息，但长标题只能两行截断；详情是完整信息的兜底。
- **项目很多**：左轨会滚动，sparkline 仍保留；超过 10 个项目时建议加「最近 / 全部」分组或折叠。
- **数据量**：需求/任务列表目前一次性渲染；生产应虚拟化，详情继续懒加载。
- **计数一致性**：顶部是「本项目」，左轨汇总是「全部项目」；实现里不要复用同一个数字却不改标签。每次 mutation 后统一刷新或乐观更新两处。
- **无障碍**：原型有 aria-current、dialog、焦点进入和 Esc；生产需要补完整的焦点陷阱、抽屉关闭后的焦点返回、toast 的 `aria-live` 已有、错误与禁用态。
- **设置层级**：原型只呈现项目设置卡和系统设置说明，不展开表单；正式实现应继续沿用现有的系统/项目设置页，不把两者合并。
- **评审推进**：本地状态推进仅用于演示；服务端返回的状态必须覆盖本地推断。
- **命令面板**：当前只检索已加载的当前项目需求/任务，跨项目是切换而不是全文搜索；正式实现可以接入服务端搜索，或把现有 Header 搜索与面板合并。
- **未覆盖**：移动端、审计页、完整设置页、需求编辑/关闭、任务新建独立表单（任务从拆分产生，符合现有产品语义）。
